# 三个设计取舍

## 1. 人工确认是后端状态门槛

**问题：** 模型可能对材质、功效等作出推断，前端勾选也可被绕过；重新识图后旧方案可能继续被提交。

**方案：** 服务端保留原高风险字段，拒绝删除、降级或未确认；允许“未知”保持未知。策划绑定已确认识图版本，创建批次再次验证最新版本与确认状态。

**原因与代价：** 让人工决策有可检查的状态边界，代价是操作步骤增加和上游变更后需要重新确认。当前只是最小版本关联，不是完整内容依赖哈希图。

**验证：** [风险不能绕过](../checks/test_workflow_postgres.py#L48)、[重新识图使旧方案不可提交](../checks/test_workflow_postgres.py#L290)。

## 2. 五张图是五个任务，重试只改变失败项

**问题：** 整批重做会浪费已成功结果，重复提交又可能建立相同批次。

**方案：** 幂等键按 owner、method、path 查找，并比较请求内容摘要；同键不同内容返回冲突。批次拆分逐项状态，手动重试只把 failed 的 initial 项排回队列，保留已成功图片及 ID。

**原因与代价：** 任务、进度、错误和尝试次数更透明，代价是子项状态聚合、重试竞争与事件一致性更复杂。幂等语义按接口分别说明，不把创建批次的保证推广到所有同步操作。

**验证：** [8 并发同键创建](../checks/test_workflow_postgres.py#L83)；[4+1 重试保持四张结果](../checks/test_workflow_postgres.py#L109)。视频同时显示可复核的 [1,1,2,1,1]。

## 3. Redis 可重复投递，数据库裁定执行归属

**问题：** 消息重复、进程退出或租约过期后旧进程恢复，都可能让同一项被多次执行。

**方案：** CAS 从 queued 领取，建立 lease_token 与递增 attempts，心跳不复活过期租约；调用结束后匹配 token、代次、状态、有效租约才写结果。恢复进程检查过期项和已提交 queued 项，SSE 与轮询读取持久化事件和历史。

**原因与代价：** 不依赖“队列绝不重复”，但新增短全局锁会限制吞吐；数据库状态和媒体卷不是分布式事务。接管可能重复外部请求，不能承诺外部调用与计费严格一次。

**验证：** [真实 kill/旧成功/旧错误拒绝](../checks/test_workflow_postgres.py#L222)；[独立 Dramatiq](../checks/test_workflow_postgres.py#L262)；[终态事件续读](../checks/test_workflow_postgres.py#L143)。
