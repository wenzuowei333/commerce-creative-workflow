# 面试讲解

## 90 秒介绍

我独立开发过电商商品视觉策划与生图平台，这个脱敏仓库保留了从参考图、商品识别、人工确认、视觉策划到批量结果的四步工作台。它解决的不只是调用生图接口，还包括用户确认过什么、哪一项失败、重复点击会不会创建两批任务，以及刷新后能否恢复。

这里有三个重点：第一，风险字段和方案版本由后端校验，不能靠前端勾选保证；第二，一个批次拆成逐图任务，用幂等键和内容摘要处理重复提交，重试只改变失败项；第三，Redis/Dramatiq 消息可以重复，数据库用条件领取、租约和执行代次决定谁能写回。

演示中第 3 张首次失败，刷新后状态仍在；重试后尝试次数是 [1,1,2,1,1]，其他四张成图 ID 不变。阶段五有 42 项源回归、21 项 PostgreSQL/Redis 集成、7 项前端测试和 3 组浏览器用例。本版只用合成参考图和 Mock 占位输出，验证工作流与恢复机制，不评价真实模型效果。完整依赖哈希图和混合检索不在这个候选范围内。

## 常见追问

**为什么队列外还要数据库状态？** 消息可重复或丢在提交后的间隙。数据库裁定当前项状态与执行权，恢复进程扫描持久化 queued/过期项，再投递消息。

**进度为什么 100% 仍有失败？** 它表示本轮已终结项比例；成功、失败和待执行数量分别展示，不能把完成度当成功率。

**批次快照能保证历史完全复现吗？** 不能。它冻结尺寸、质量等方案设置；参考素材仍按执行时读取，没有完整的内容哈希失效图。

**一次领取是否等于一次收费？** 不等于。租约丢失时可能已有外部调用；本版只约束本地结果回写，真实外部幂等和账单核对需另行实现。

**怎样证明模型识别准确？** 当前视频不能证明。需要真实模型、标注样本、固定版本、重复次数和错误分类的独立评测，不能引用 Mock 置信度。
